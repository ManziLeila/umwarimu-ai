## Backend — Google Sheets / Apps Script

Umwarimu AI's data layer is Google Sheets + Google Forms, automated with a
single shared Apps Script project (version-controlled here via
[`clasp`](https://github.com/google/clasp), not edited in the browser
editor). See [`apps-script/`](apps-script) for the source. Full architecture
rationale lives in this repo's plan history; the short version:

- One Apps Script project serves **every** school. It resolves which
  school's spreadsheet to read/write per request — there is no
  copy-pasted script per school.
- A **Master Registry** spreadsheet holds one row per school (`Schools`
  tab) and a global `email -> school, role` lookup (`Staff` tab).
- Each school gets its own spreadsheet + two Forms (Scores, Attendance),
  cloned from a template by `onboardSchool()` — never hand-copied.
- The existing Node/TanStack Start server in this repo is the only thing
  that talks to the Apps Script web app; the browser never calls it
  directly, and student/attendance data never touches a client bundle.

### One-time setup (requires your own Google account — cannot be scripted)

```sh
cd apps-script
npm install
npx clasp login                          # opens a browser for Google OAuth
npx clasp create --type webapp --title "Umwarimu AI" --rootDir ./dist
npm run build && npx clasp push
npx clasp open                           # opens the Apps Script editor
```

In the editor: set **Project Settings > Script Properties** —
`APPS_SCRIPT_API_KEY` (a long random string, shared with the Node backend's
`.env`) and `GEMINI_API_KEY`. Then select and run the `runBootstrap`
function once (Apps Script will prompt you to authorize the scopes in
[`appsscript.json`](apps-script/appsscript.json) — this consent step is
exactly why bootstrapping can't be automated end-to-end). It creates the
Master Registry and the per-school template spreadsheet/forms and writes
their IDs back into Script Properties automatically. Then run
`runInstallTriggers` once to install the two shared triggers (see
[Known limitations](#known-limitations)).

Deploy the web app (`npx clasp deploy`) and put the resulting URL in
`APPS_SCRIPT_WEB_APP_URL` in your root `.env` (copy `.env.example` first —
never commit `.env`).

### Onboarding a new school

Either call the deployed web app's `onboardSchool` action from the Node
backend, or from a terminal:

```sh
node scripts/onboard-school.mjs \
  --school-id=kigali-01 --name="Groupe Scolaire Kigali" --district=Kigali \
  --admin-email=admin@school.rw --admin-name="Jean Bizimana"
```

This clones the template spreadsheet and both forms, points the forms'
responses at the new spreadsheet, shares everything with the admin (and any
`--staff-emails=a@x,b@x`), and registers the school — no manual copying.

### Where secrets/config live

| Secret | Where |
|---|---|
| `APPS_SCRIPT_API_KEY`, `GEMINI_API_KEY` | Apps Script Script Properties (server-side, never in source) |
| `GEMINI_API_KEY`, `APPS_SCRIPT_WEB_APP_URL`, `APPS_SCRIPT_API_KEY`, `GOOGLE_OAUTH_CLIENT_ID` | root `.env` (see `.env.example`), used by the Node server, never sent to the browser |
| Per-school thresholds (low-score %, attendance %) | that school's own `Config` sheet tab |

### Known limitations

Apps Script is free-tier and has real quotas — documented in full in the
architecture plan, summarized here:

- **Triggers per script are capped at 20/user.** A naive per-form
  `onFormSubmit` trigger design would exhaust that by roughly the 10th
  school. This project uses exactly **two** shared installable triggers
  total (a ~10-minute poll-and-validate sweep, and a nightly at-risk sweep),
  regardless of school count.
- **`MailApp`/`GmailApp` is capped at 100 recipients/day on a personal
  Gmail account** (1,500+ on Google Workspace, including the free Workspace
  for Education tier). A single mid-size school's alert emails can exceed
  100/day on its own — **run this project under a Workspace account, not a
  personal @gmail.com**, once it's handling real alert volume.
- **6-minute execution limit per run.** The nightly/poll sweeps loop over
  every school in one execution; if school count grows large enough to risk
  that ceiling, the loop needs a "last processed" checkpoint so a run can
  stop and resume instead of timing out mid-sweep.
- **`UrlFetchApp` (used for Gemini calls in alert generation only — chat
  traffic goes through the Node server, not Apps Script) is capped at
  20,000 calls/day**, comfortable at the volume this design produces
  (roughly one call per flagged student per week).
- **Where this stops being enough:** sub-second concurrent access for many
  simultaneous users, true relational joins across schools, or sweep volume
  that no longer fits in 6-minute batched runs are the signal to move the
  data layer to a real database + small API service — keeping the same
  JSON API contract so the frontend and onboarding flow don't need to
  change.
